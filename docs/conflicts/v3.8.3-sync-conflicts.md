# Conflict audit: upstream sync v3.5.0 -> v3.8.3

Repo: omarchy-mac-fedora. Target branch: `sync/upstream-v3.8.2` (branched from `dev`; the branch keeps
its name, the sync went one tag further).
Upstream source: https://github.com/basecamp/omarchy, tags fetched under `upstream/*`.
Base of the sync: `upstream/v3.5.0` = 76d09b29 (already an ancestor of `dev` - true 3-way base).

Strategy: one `git merge --no-ff` per upstream tag (never rebase, never squash), so every merge commit
carries both parents and its conflict resolution is legible in history. Fork-side invariants that win
every conflict: dnf not pacman; aarch64 only (skip Intel/NVIDIA/Framework/ASUS/Surface/Dell/T2/Lenovo
x86 hardware); alacritty not ghostty; dracut not mkinitcpio/limine.

Each tag section lists the merge SHA, both parents, and one line per conflicted file on how it was
resolved and why.

# WS3 - Fedora 44 support

The bump alone does not make the installer run: it was broken on Fedora 44 for reasons that have
nothing to do with the version bump. Every fix below is proved by `tests/verify-f44-container.sh`,
which resolves the whole package set against a real fedora-44-aarch64 repository set in an emulated
container. It exits 0 on this branch.

## COPR repositories (`install/helpers/fedora-copr.sh`)

| Change | Why |
|---|---|
| Remove `pgdev/ghostty` from `COPR_REPOS` | **The #1 root cause.** The COPR project does not exist. It sat in the *required* list, whose loop `exit 1`s on failure, so the installer died on every Fedora release, not just 44. |
| Add `scottames/ghostty` to `OPTIONAL_COPR_REPOS` | The real home of Ghostty (f44-aarch64 chroot, ghostty 1.3.1-2 built). Optional, not required: the default terminal is alacritty and `omarchy-install-terminal ghostty` is a user choice - a missing Ghostty must never fail an install. Credit: david-kerins (PR #17) independently found the ghostty breakage. |
| Add `hyprland-qt-support` to solopasha's `excludepkgs` | It is in the base package list and is built by *both* lionheartp and solopasha. Only `priority=10` vs `90` kept DNF on the right one; if lionheartp's build ever goes missing, DNF would silently fall back to solopasha's Hyprland-0.49-era build. |
| Required-repo failure now names the release and arch | `dnf copr enable` failing told the user nothing. |
| Repo protections extracted to `install/helpers/fedora-copr-protect.sh` | The installer and the repair migration must apply *the same* protections. One definition, two callers. |

Kept as-is: the `technochip` -> `lionheartp/Hyprland` rename (already on `dev`, commit `eb078af5`), its
`priority=10`, and `exclude=gtk4* gtk3* pango* cairo*` (core GTK stays on Fedora's build).

### webp-pixbuf-loader: the name resolves, the loader does not exist

`dnf install webp-pixbuf-loader` **succeeds** on Fedora 44 - `gdk-pixbuf2` carries
`Obsoletes: webp-pixbuf-loader <= 0.2.7-4`, so the name is satisfied. That is not the same as webp
working. Evidence from the fedora-44-aarch64 repodata:

- `dnf repoquery --whatprovides webp-pixbuf-loader` -> `gdk-pixbuf2` (the Obsoletes tag)
- `dnf repoquery -l gdk-pixbuf2 | grep -i webp` -> nothing
- `dnf repoquery --file "*pixbufloader-webp*"` -> nothing, in any repository
- the only gdk-pixbuf loader left in Fedora 44 is `libpixbufloader-xpm.so` (`gdk-pixbuf2-modules-extra`)

Fedora moved image decoding for GTK4 to **glycin**, so `glycin-loaders` (which ships `glycin-image-rs`)
is what actually renders webp/avif/jxl now. Keeping the old name in the list would have looked green in
every check while quietly rendering nothing. Device check on the MacBook: webp images in `imv` (not a
GTK4 app) and in Nautilus.

## Fedora 44 only, with no Fedora 43 user left in limbo

`install/helpers/distro.sh` gains `fedora_version()`, `is_fedora_supported_version()` and
`fedora_upgrade_instructions()`. The gate stops the run and prints the upgrade path at every entry
point, and **never** runs `dnf system-upgrade` itself - that reboots the machine and can leave an Asahi
install unbootable.

| Entry point | Behaviour below Fedora 44 |
|---|---|
| `install/preflight/guard.sh` | hard stop before anything is installed (not the soft `abort` - a half-installed 3.8.2 is worse than no install) |
| `bin/omarchy-update-perform` | refuses the whole update pipeline before the first package is touched |
| `bin/omarchy-migrate` | refuses to run any migration |

**The gate cannot be a migration.** Migrations run in timestamp order, so a migration added today sorts
*after* all 63 upstream migrations and would only fire once they had already run. It has to be in the
code that drives them. Proved by `tests/verify-f43-gate.sh`: on an emulated fedora-43-aarch64 container
`omarchy-migrate` exits non-zero, prints the instructions, and marks **0** migrations as applied; on
fedora-44-aarch64 the gate does not fire.

## Source-built packages: walker and elephant

Neither is in Fedora or in any COPR, so `install/helpers/fedora-walker-elephant.sh` builds them (walker
= Rust/cargo, elephant = Go, plus 9 provider plugins). Three defects found while verifying that the
build still matches upstream's projects:

1. **An existing install could never be upgraded.** The script exited early whenever a `walker` binary
   existed, without looking at its version. A user on 3.5.0 would have kept the 3.5.0-era launcher while
   Omarchy 3.8.2 shipped Walker/Elephant configs (unlock menu, symbols shortcut, Hyprland 0.55
   dispatchers) that need the new one. Fixed with pinned versions (walker `v2.16.2`, elephant `v2.21.0`)
   and a version stamp at `~/.local/state/omarchy/walker-elephant-version`.
2. **Version pinning was broken.** The script cloned `--depth=1` and *then* checked out the tag - a
   shallow clone does not have the tag's objects. Nobody noticed because the pin defaulted to empty, so
   every install silently built the default branch (an unreleased HEAD). Now the ref is selected at
   clone time.
3. **Updates never rebuilt them.** `dnf upgrade` cannot move a source build. New `bin/omarchy-update-manual-pkgs`
   runs in `omarchy-update`, is a no-op when the stamp matches the pin, and rebuilds (and restarts the
   launcher) when it does not. Elephant's providers are Go plugins and are version-locked to the binary,
   so they are always rebuilt with it.

Verified against the upstream projects: walker is still a Cargo project (`Cargo.toml`, latest release
v2.16.2), elephant is still Go (`go.mod`, `cmd/elephant`, latest v2.21.0), and every provider the
script builds still exists under `internal/providers/`.

The same blindness applied to the cargo-installed TUIs: `install_cargo_tool` only checked whether the
command existed, so `impala` and `wiremix` were frozen at whatever version an install first built.
They are now checked by *version* against `cargo install --list` and rebuilt with
`cargo install --locked --force` when the pin moves; `wiremix` is bumped to its current release
(0.11.0), `impala` stays at 0.7.3 (already current). `omarchy-update-manual-pkgs` runs both helpers, so
a normal update is two version checks and nothing else.

Elephant's `dnfpackages` provider is now built as well (search and install DNF packages from the
launcher). It is one more `go build -buildmode=plugin` out of the source tree that is already being
compiled - no new toolchain, no new dependency; it drives the `dnf` CLI through `os/exec`.

`bin/omarchy-pkg-drop` carried a dead `sudo pacman -Rns` branch (its `installed` array was never
populated, so it could not fire). Removed - `dnf remove` is the only path in a Fedora fork.

## The Wi-Fi backend swap was not actually atomic

`install/post-install/network-finalize.sh` runs dead last in the pipeline, after every package and build
step, which is right: it swaps the machine's only network link out from under itself. But
`install/config/hardware/network.sh` - which runs in the middle of the install - already did
`systemctl enable iwd.service`, while NetworkManager was still on the wpa_supplicant backend.

That is a half-swap that survives a reboot. If the install is interrupted anywhere between the two
steps, the next boot starts iwd *and* wpa_supplicant, both claiming the Wi-Fi device, on a laptop whose
owner now has no way to get back online to fix it.

The enable is gone from the config step; the swap is one operation at the end, and it now rolls back.
`enable --now iwd` failing, iwd not actually coming up, or NetworkManager failing to restart each
restore the working wpa_supplicant setup (backend config removed, iwd disabled, wpa_supplicant back)
rather than leaving the machine pointed at a backend that is not running.

## Lint regression the merge introduced

The fork's CI runs `shellcheck -S error` over every script except `migrations/`. The merge brought in 16
upstream files with no shebang (`install/config/hardware/{asus,intel,lenovo}/*`, `install/config/pi.sh`,
`install/config/user-dirs.sh`, `install/first-run/swayosd.sh`, ...) which fail SC2148, plus
`install/config/hardware/intel/ptl-kernel.sh`, whose conflict resolution had left a duplicated header
and a shebang on line 2 (SC1128). `dev` was green, so this was a regression the merge would have taken
straight into a red PR. Shebangs added; `ptl-kernel.sh` restored to upstream's content.

### `bin/omarchy-npx-install` - bun via mise, not dnf

The npx wrappers install a bun runtime when an npm package ships a bun shebang. The merged wrapper did
`omarchy-pkg-add bun`, which routes to `dnf install bun` - **bun is not a Fedora package and is in no
COPR**, so the first user with a bun-shebanged tool would have hit a hard failure. It is a mise-managed
runtime; the fork's own `bin/omarchy-install-dev-env` already does `mise use -g bun@latest`. The wrapper
now does the same.

## This release's own migrations

| Migration | What it does |
|---|---|
| `1783927940` | Removes the dead COPR repo files (`technochip/Hyprland-aarch64` - no f44 chroot; `pgdev/ghostty` - never existed), makes sure `lionheartp/Hyprland` is enabled, and re-applies the priority/exclude protections through the shared helper. Never leaves two Hyprland COPRs enabled. |
| `1783927950` | Brings the package set to what Fedora 44 actually has: `java-21-openjdk` -> `java-latest-openjdk`, `gst-plugin-pipewire` -> `pipewire-gstreamer`, `wget` -> `wget2-wget` (a swap, not an install: both own `/usr/bin/wget`), drops `yaru-gtk2-theme` and `webp-pixbuf-loader`, adds `glycin-loaders`, `socat`, `mesa-vulkan-drivers`. Every step is `rpm -q`-guarded. |
| `1783927960` | Rebuilds walker + elephant at the pinned versions and restarts the launcher. No-op when the version stamp already matches. |

Each was run twice in an emulated fedora-44-aarch64 container (`tests/verify-migrations-container.sh`):
both runs succeed and the second run changes nothing - no packages, no repo files, no state.

The harness then stages the state that actually matters - a machine that came up from Fedora 43, with
the retired packages still installed (pulled with `--releasever=43`) - and runs the package migration
against it. That is what caught the last bug in it: **`gst-plugin-pipewire` and `wget` were never real
packages on Fedora 43 either** (both resolved through `Provides` tags), so `rpm -q` never sees them,
so a swap-only migration would have quietly left an existing user with **no `pipewire-gstreamer` at
all**. The migration now guarantees the end state rather than performing a swap: replace the old name
if rpm has it, otherwise just make sure the successor is installed.
